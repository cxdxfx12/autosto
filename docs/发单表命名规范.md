# 发单表（Excel）命名规范

> 目的：避免重名文件在微信/Windows 落盘时自动加 `(1)` `(2)` 后缀，导致程序把「同一批单」误判成「找不到文件」而丢单。
> 这是 **1.1.4 修过的一个真实事故** 的源头，规范命名能从根上不再触发它。

---

## 0. 事故复盘（为什么要有这规范）

2026-10-29 出现「有新单号不揽收」：业务员在微信群里发的 `X (2).xlsx`，被微信下载到本地时因为同名已存在，自动变成 `X (2)(1).xlsx`。
程序按「文件名去掉 `(N)` 后缀」去匹配，结果两种后缀叠在一起没剥干净 → 判定文件「本地找不到」→ 整批单号没入库。

- 程序侧已修：`scan/extract/wechat.py` 的 `base_stem()` 现在循环剥离所有 `(N)` 后缀，且「本地找不到」会写 **warning** 日志（搜 `scan.log` 里的「本地找不到」即可定位）。
- 但**规范命名更省心**：文件名本身带日期时段，永远不会和昨天的重名，从源头杜绝 `(1)` 后缀。

---

## 1. 推荐格式

```
MMDD_时段.xlsx
```

| 要素 | 写法 | 例子 |
|---|---|---|
| 月份+日 | `MMDD`（2 位月 2 位日） | `1103` |
| 时段 | 上午 / 下午 / 晚上 / 凌晨，或具体区间 | `晚上` `0900-1100` |
| 后缀 | `.xlsx` | — |

**示例**：
- `1103_晚上.xlsx`
- `1103_0900-1100.xlsx`
- `1103_下午.xlsx`

> 也可以用你习惯的 `10.29晚上.xlsx`（点分隔）风格——只要**每批一个不重名的名字**即可，程序对文件名里的点是兼容的。推荐 `MMDD_时段` 只是因为它排序友好、跨年也不混。

---

## 2. 规则（记住这 4 条）

1. **每批一个文件、一个不重名的名字**：同一个 `.xlsx` 反复发，微信/Windows 就会加 `(1)` `(2)`。
2. **名字带日期 + 时段**：今天和昨天的表天然不撞名，永远不会触发 `(1)` 后缀。
3. **别用含糊词**：`最终版` `改` `新建文件夹(2)` `新建 Microsoft Excel 工作表` 这类名字要么会重名、要么看不出是哪批。
4. **一个批次不要拆成多个文件再合并**：拆开容易漏、容易重名。一批货一张表。

---

## 3. 出错怎么排查

如果某批单号「没收进去」，按这个顺序查：

1. 看程序界面「导入」记录，确认文件有没有被读到。
2. 翻 `data/scan.log`，搜 **「本地找不到」** —— 命中就说明是文件名 `(1)` 后缀错位（老版本才会；1.1.4+ 已能自动剥，但仍建议规范命名）。
3. 确认微信下载目录里同名文件是不是被加了 `(1)`：把表改成带日期时段的名字再发一次即可。

---

## 4. 一键生成规范名（工具）

仓库里带了 `tools/naming.py`，可以：

```bash
# 给一个基础名，按当前时间生成规范名（默认只打印，不动文件）
python tools/naming.py "发单表"
# → 1103_晚上.xlsx

# 指定时段
python tools/naming.py "发单表" --period 0900-1100
# → 1103_0900-1100.xlsx

# 扫描某个目录，预览每个 xlsx 会被改成什么（干跑，不改名）
python tools/naming.py --scan inbox/
```

`--scan` 是只读预览；要真改名加 `--apply`（**改名前请确认程序没在导入该目录**）。

---

## 5. 给业务员的口头版

> 「每次发揽收表，文件名带上今天日期和时段，比如 `11月3日晚上.xlsx`、`1103下午.xlsx`。
> 别用『最终版』『新建表格』这种名字，也别把同一张表反复发——重名会被系统自动加 (1)，可能丢单。」
