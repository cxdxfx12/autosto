# 微信 4.x「UIA 空壳」根因分析与解法

> 归档日期：2026-10-29
> 涉及版本：本程序 1.1.3 / 微信 4.1.15.53（Weixin.exe）
> 结论级别：已定位根因、已落地代码、已验证采集恢复

---

## 一、症状

点「立即抓取」报「找不到微信群 / 会话列表里找不到群」，实际上是**微信根本没有暴露控件树**。

典型表现：

| 现象 | 说明 |
| --- | --- |
| 微信顶层窗口 ClassName = `Qt51514QWindowIcon` | Qt 空壳窗口，UIA 子节点数 = 0（或符号性 3 个） |
| 找不到 `mmui::MainWindow` | 程序判定的主窗口类名不存在 |
| 界面上微信显示完全正常 | 界面画出来了，但无障碍树没构建 → 人眼看着没毛病 |
| 重启微信 | 无效 |
| 点「进入微信」 | 偶尔短暂恢复正常，几秒后**又变回壳** |
| 禁 GPU（`--disable-gpu`） | 无效 |
| 软渲染（`QT_OPENGL=software`、`QT_ANGLE_PLATFORM=software`） | 无效 |

关键误导点：**之前一段时间一直是好的**，某天重启后就再也回不来，看起来像「微信升级了」「登录态坏了」「转发桥搞坏了」，全不是。

---

## 二、根因

微信 4.x 使用自绘 UI（mmui 框架）。Qt 层有一道**「无障碍闸门」**：

> 只有检测到系统 / 客户端正在使用无障碍（读屏）能力时，微信才会真正构建 `mmui` 控件树；
> 否则只创建一个 Qt 空壳窗口，把界面画出来就完事。

这个闸门的状态保存在 `Weixin.dll` 的一个**运行时字节**里，**冷启动默认为 0**。

所以：

- 重启微信 → 冷启动 → 闸门还是 0 → 还是空壳（重启多少次都没用）
- 点「进入微信」→ 只是界面上跑完登录流程，不碰闸门 → 短暂可能被某个偶然事件顶起来，很快又落回 0
- 禁 GPU / 软渲染 → 属于渲染路径，与无障碍树构建无关 → 无效
- 「昨天还是好的」→ 只是因为昨天那一次启动，闸门恰好处于开的状态（例如某个 UIA 客户端曾经接入过）

**这解释了一切矛盾现象**：界面正常、人能操作、程序读不到任何控件。

---

## 三、解法

### 3.1 核心动作

找到 `Weixin.dll` 里的闸门字节（版本相关 RVA），把它**保持为 1**。

### 3.2 关键发现：写一次不持久

微信自己会把该字节改回 0，实测只顶几秒。因此必须**常驻保持**：

```
每 0.25 秒检查一次
  如果当前值 != 1 → 写入 1
```

只写 1 个字节，写的是「读屏客户端存在」这个状态位本身，不改任何代码逻辑；微信重启后自然复位，对微信无持久副作用。

### 3.3 本机实测参数

| 项 | 值 |
| --- | --- |
| 微信版本 | 4.1.15.53 |
| 安装路径 | `D:\Program Files\Tencent\Weixin-new\Weixin\Weixin.exe` |
| 闸门 RVA（相对 `Weixin.dll` 基址） | `0xB3959D8` |
| 保持频率 | 0.25 秒 |
| 进程访问 | `OpenProcess` + `ReadProcessMemory` / `WriteProcessMemory` |

### 3.4 版本漂移怎么办

微信升级后 RVA 会变。参考实现自带**扫描器**：在 DLL 里按特征字节序列查找候选地址，逐个试写 + 读回校验，失败自动回滚。

代价：纯 Python 逐字节扫整个 DLL 要几十秒。为此做了两层优化：

1. **版本表直命中**：`QACCESSIBLE_ACTIVE_RVA_BY_VERSION` 里已知版本直接用 RVA，不扫描
2. **按 DLL 路径缓存**：同一路径扫描结果只算一次

否则常驻线程会长时间卡在扫描里（首次上线时真踩过，线程栈就停在扫描函数）。

## 五、现场排障命令

```bash
# 只读诊断：列出微信窗口类名、进程、DLL 基址、候选 RVA、闸门当前值
python -m scan.extract.wechat_gate status

# 一次性热激活（不重启微信，写 1 字节 + 校验）
python -m scan.extract.wechat_gate wake

# 前台常驻保持（临时排障用，正常由程序自带）
python -m scan.extract.wechat_gate keeper
```

判断依据：`status` 输出里看窗口 ClassName。

- `mmui::MainWindow` → 正常，控件树可用
- `Qt51514QWindowIcon` → 空壳，闸门没开
- `mmui::LoginWindow` → 停在登录确认页，需要人点「进入微信」

## 七、走过的弯路（避免重复走）

| 尝试 | 结果 | 原因 |
| --- | --- | --- |
| 重启微信（多次） | 无效 | 冷启动闸门恒为 0 |
| 点「进入微信」 | 短暂恢复后回落 | 不碰闸门字节 |
| 等登录页出现再点 | 无效 | 同上 |
| `--disable-gpu` 启动 | 无效 | 渲染与无障碍树无关 |
| `QT_OPENGL=software` 等软渲染 | 无效 | 同上 |
| `SPI_SETSCREENREADER` 单独调用 | 不够 | 返回 ok 但 `GetSystemMetrics` 读不到，且微信不认 |
| 启动 Narrator.exe | 无法执行 | 本机是 Server 精简镜像，没有 Narrator.exe |
| 改注册表 UIA 相关键 | 未采用 | 影响面大，且非闸门本体 |
| 怀疑转发桥 hook 微信 | 已排除 | 桥停掉后仍空壳 |

## 八、与转发桥共存说明

`D:\wxauto-main\ddwx-bridge` 也在操作同一个微信。该项目的 10-18 记录里同样撞过这个坑。两者都靠 UIA 读微信，**闸门只影响「有没有控件树」，不影响谁在写字节** —— 谁保持都可以，不冲突。

它们的自愈巡检（打开最近任务 / 拉起钉钉）会抢前台，与揽收动作冲突，那是另一个问题，已有 `phone_arbiter.ask_peer_yield()` 让路机制处理。
