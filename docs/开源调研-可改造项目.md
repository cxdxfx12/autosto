# 开源方案调研｜有没有现成的可以拿来改（2026-10-19 实测）

> 检索方式：GitHub Search API 实跑 12 组关键词（中英文各半），逐条用 `/repos` 接口核实**星数、最近提交、许可证**，不用印象判断。
> 结论对「从微信群/Excel 取号 → 驱动申行者揽件扫描」这个组合负责。

---

## 0. 结论先说

**没有端到端的现成方案，一个都没有。**

| 搜什么 | 结果 |
|---|---|
| `申行者` | 仓库 0 个（连山寨都没有） |
| `申通 揽收` | 仓库 0 个 |
| `运单号 扫描 自动化` | 0 个 |
| `waybill scanner android` | 2 个，都是 ★0 的玩具 |
| `express delivery automation android` | 0 个有效结果 |

原因很直白：这类活是「自家业务系统 + 自家手机 + 自家账号」，做成了也不会开源，开源了也没有第二个人能用。

**但零件层非常成熟**——手机自动化、文本输入、HID 键盘、微信 UIA 都有万星级项目。所以正确的姿势不是「找个项目 fork」，而是**拿 4 块积木自己拼**，工作量能比从零少一半。

## 1. 可以拿的四块积木

### 1.1 手机执行层（核心，决定成败）

| 项目 | 星 | 许可 | 最近提交 | 拿什么 | 不能拿什么 |
|---|---|---|---|---|---|
| **`openatx/uiautomator2`** | ★8429 | MIT | 2026-10-18 | `d(text=).set_text()` / `dump_hierarchy()` / `click()`，P0 探针当天就能跑；也能直接当生产执行器（PC 侧全权控制） | 依赖 adb；手机重启后 WiFi 连接失效，要重新插线 |
| **`SuperMonster003/AutoJs6`** | ★6503 | MPL-2.0 | 2026-03-16 | JS 脚本 + 无障碍，**手机上直接跑，不用编译 APK**。写 30 行就能「轮询 HTTP → setText → click → 回报」，用来 2 小时验证整条链 | 依赖第三方运行时 App；Android 13+ 侧载要手动「允许受限设置」；脚本暴露、不好做设置页和保活 |
| `AirtestProject/Airtest` | ★9610 | Apache-2.0 | 2026-03-23 | 图像识别定位（`touch(Template("确定.png"))`），**申行者若是自绘 UI，这是不买硬件的最后一条路** | 慢（每步截图匹配 0.3–1s），50 单会拖到十几分钟 |
| `gkd-kit/gkd` | ★43044 | **GPL-3.0** | 2026-10-16 | 只借**设计**：它的「高级选择器 + 订阅规则 + 触发条件」是同类里做得最好的 | 代码一行都别抄，GPL 会传染整个 APK |

> 为什么不用 Appium（★22097）和 STF（★4609）：它们是为「多设备测试农场」设计的，装完一套比我们整个项目还重，收益为零。

### 1.2 文本输入兜底（很可能用得上）

| 项目 | 星 | 许可 | 用途 |
|---|---|---|---|
| **`senzhk/ADBKeyBoard`** | ★1967 | GPL-2.0 | 装成输入法，用广播 `am broadcast -a ADB_INPUT_TEXT --es msg 77123...` 往焦点框塞字。**当 `setText` 被 App 拦截、或输入框是自绘控件时，这是最省事的绕法** |

注意：单号是纯数字，`adb shell input text 7712345678901` 本来就能打（不需要中文输入法）。ADBKeyBoard 主要解决「有焦点但 setText 无效」的情况。
GPL-2.0 只装不链（它是独立 App），不传染我们的代码；但**别把它的源码拷进我们的 APK**。

### 1.3 硬件兜底（只有控件完全不通才用）

| 项目 | 星 | 许可 | 说明 |
|---|---|---|---|
| `T-vK/ESP32-BLE-Keyboard` | ★3178 | **无 LICENSE 文件** | 事实上的 ESP32 BLE HID 标准库，但没写许可 = 保留所有权利，商用要谨慎 |
| `gayandsilva/ESP32-BLE-Barcode-Scanner` | ★0 | 未标 | 结构可参考（GM67 模块 + BLE HID），代码量很小，照着自己写更快 |

更好的做法：**用 Arduino 的 `BleKeyboard`（有 MIT 分支）自己写 60 行**，别背无许可代码的包袱。

### 1.4 微信采集层

| 项目 | 星 | 许可 | 判断 |
|---|---|---|---|
| `cluic/wxauto` | ★7374 | Apache-2.0 | **不能用**。它自己的注释写着：微信 4.x 窗口类变成 `mmui::MainWindow` 后「wxauto 3.9 的窗口定位逻辑直接失效」。但它的 `uiautomation` 封装可以借来当 UIA 底座 |
| `LC044/WeChatMsg` | ★42101 | 无许可 | **用不上了**。UIA 已经能直读正文，不需要解密数据库（省掉 WeChatMsg 对 4.1.15 支持存疑这个风险） |
| **ddwx-bridge 的 `bridge/targets/wechat4.py`** | 自家代码 | — | **最值钱的一块**。1084 行、实战验证过的 `mmui::` 选择器表，见下节 |

## 2. 顺手确认的宝贝：微信 4.x 选择器表（ddwx 已在生产验证）

`wechat4.py` 的注释直接给出了映射，`wechat_tree.txt` 也验证过：

| 位置 | 控件 | 用途 |
|---|---|---|
| 主窗口 | `mmui::MainWindow` | 定位微信 |
| 会话列表 | `mmui::XTableView` → `mmui::ChatSessionCell` | 切群 |
| 群名标题 | `mmui::ChatTitleBarMasterView` | **护栏：不是目标群就不采** |
| 消息列表 | `mmui::RecyclerListView` | 滚动容器 |
| **消息正文** | **`mmui::ChatTextItemView` → name = 文本内容** | 取单号 |
| **时间戳** | **`mmui::ChatItemView` → name = 时间** | **必须过滤，否则 `12:25` 会被当成一条消息** |
| 文件/图片 | `mmui::ChatBubbleItemView` → name = `文件\nxxx.xlsx` | 只拿得到文件名 |

原文写得很清楚：**「实测微信 4.1.x 仍然向系统暴露 UIA 控件树」**——这句话就是 P2 可行性的证据。

## 3. 三条拼装路线

### 路线 R1｜AutoJs6 打样（0.5 天，只为验证，不做生产）
手机上装 AutoJs6 → 粘一个 `.js`：

```js
// 伪代码：轮询 PC 队列 → 填号 → 点确定 → 读结果
while (true) {
  let job = http.get("http://192.168.1.x:8766/scan/jobs?token=xxx").body.json();
  if (!job.job) { sleep(2000); continue; }
  let box = className("android.widget.EditText").findOne(3000);
  if (!box) { report(job.job.id, "fail", "找不到输入框"); continue; }
  box.setText(job.job.waybill);
  text("确定").findOne(2000).click();
  sleep(2500);
  report(job.job.id, "ok", 读当前屏文本);
}
```

**价值**：一个下午就能证明「申行者到底吃不吃 setText」。如果通，后面所有工作都是工程化；如果不通，立刻转 ESP32，不浪费一周。
**风险**：AutoJs6 需要无障碍权限，Android 13+ 侧载 App 要在「应用信息 → 允许受限设置」里放行，第一次装会卡一下。

### 路线 R2｜自家 APK（5–7 天，做生产）
基座直接照抄 `ddwx-bridge/android`（1869 行，已跑在生产上）：

| 现有文件 | 复用方式 |
|---|---|
| `CollectorService.java` | 保留服务骨架、心跳、事件节流；把「读树上报」换成 `ScanWorker` |
| `UiTree.java` | 直接用（找节点、取文本） |
| `Scroller.java` | 申行者要滚动列表时用 |
| `Uploader.java` | 改成两个端点：拉任务 / 报结果 |
| `Prefs.java` + `MainActivity` | 配置页（服务器地址、token、批量上限、开始/暂停） |
| `KeepAliveService` | 保活，插电常亮场景够用 |

**新增代码预计 500–700 行**，比从零写省 2–3 天，而且错误处理、重连、日志这些都是现成的。
代价：要装 Android Studio 编译（约 1 GB）。

### 路线 R3｜uiautomator2 常驻（2–3 天，不做产品）
PC 上跑 Python，全程 `d(text=).set_text()`。**当天能通，但手机重启就断**，华为还不能无线调试。
适合：P0 探针、以及 R2 还没编好时的过渡。

### 建议组合

```
P0（半天）  R3/uiautomator2 探针   → 拿到 4 个答案
P1 第一天   R1/AutoJs6 打样        → 证明全链路能跑（可选，加速信心的）
P1 主体     R2/自家 APK            → 生产执行器
不通时      ADBKeyBoard（setText 无效）→ ESP32（控件不通）
```

## 4. 许可证备忘（内部自用也建议守）

| 许可 | 项目 | 对我们的约束 |
|---|---|---|
| MIT | uiautomator2 | 随便用，保留版权声明 |
| Apache-2.0 | wxauto / Airtest / scrcpy | 可用，改动文件要标注 |
| MPL-2.0 | AutoJs6 | 改了它的源文件才需要开源该文件；自己写脚本不受限 |
| GPL-2.0/3.0 | ADBKeyBoard / GKD | **只当独立 App 装，不拷源码进我们的 APK** |
| 无许可 | WeChatMsg / ESP32-BLE-Keyboard | 严格说保留所有权利，能不碰就不碰 |

## 5. 一句话回答你的问题

**「有没有成熟方案可以搬」——整体没有，零件全有。**

最值钱的三样东西按顺序是：
1. **你们自己的 `ddwx-bridge/android`（1869 行）和 `wechat4.py`（1084 行）** —— 这两份比 GitHub 上任何项目都贴近本需求；
2. **uiautomator2**（P0 探针 + 兜底执行）；
3. **AutoJs6**（半天的可行性打样，避免一周白写）。

真正需要新写的只有两件：`ScanWorker`（拉任务/执行/回报，500 行）和 Excel/微信采集器（各 200 行左右）。
