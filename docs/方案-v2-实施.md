**关键设计与 ddwx-bridge 保持同一个哲学**（可借鉴、不 import）：
手机端做「笨」，只负责拉任务、执行、回报；所有判断（该不该扫、重试几次、什么算失败）留在 PC 的 Python 里，改规则不用重装 APK。

## 3. 采集层：三条链路怎么做

### 3.1 Excel —— 先做这个，一天能通

- 两种入口：目录监听（`inbox/*.xlsx` 丢进去就跑）+ 界面手动选文件。
- `openpyxl` 用 `read_only=True, data_only=True` 遍历**所有 sheet、所有列**，不假设列名。
- 取号规则：单元格转字符串 → 去空格/连字符 → `^\d{12,15}$` 且前缀命中（默认 `77`）。
- **必须处理的坑**：Excel 里单号常被存成数字，读出来是 `7701234567890.0`（科学计数法/浮点）。解析时先 `str(int(v))` 再走正则；**16 位以上会精度丢失，只能在源表里把列设成文本**——这个要提前跟业务员说，程序救不了。
- 合并单元格：`read_only` 下只有左上角有值，向下填充一次即可。
- 同一个文件重复丢入 → 用 `文件名+哈希` 记 `imports` 表，整表跳过，不重复入队。

### 3.2 微信群 —— 已证明可读，剩下的是工程细节

**读法**（`uiautomation`，与 ddwx 的 `wechat4.py` 同一套 `mmui::` 控件认知）：

```
微信主窗口 → mmui::ChatMessagePage
  → 子节点 ListItemControl（每项 = 一条消息）
      name = 消息全文（文本消息）/ "文件\nxxx.xlsx\n35.7K\n微信电脑版"（文件）
  → 时间分隔条：name 形如 "12:25" / "昨天 19:12" / "星期一" / "10-16"，必须摘掉
  → 群名护栏：读 ChatTitleBarMasterView，不等于配置的群名就不采（防串群）
```

- 轮询 2–3 秒，**每次读全屏快照 + 内容指纹去重**（不维护"增量游标"，微信滚动后节点会复用，增量不可靠）。
- 消息必须**自动滚动加载**才能拿到新消息——复用 ddwx `Scroller` 的思路：滚到底，等 300ms，再读。
- 约束：微信窗口**必须停在这个群、不能最小化**。`uiautomation` 只读不抢焦点，但切群要点鼠标，会打断你干活。所以：
  - 只配 1 个群（揽收专用群）→ 窗口固定在那就行，无干扰；
  - 要多群 → 得定时切换，**会抢鼠标**，建议放独立虚拟机/副屏，别在主工作机上做。
- **文件消息拿不到本体**（树里只有文件名）。两条出路，建议都留：
  1. 扫微信接收目录：`C:\Users\<你>\Documents\xwechat_files\<账号>\msg\file\<年月>\`，按 mtime 取新增 `.xlsx`，直接进 §3.1 的解析；
  2. 兜底：约定业务员把要扫的表另存到 `inbox/` 目录。

### 3.3 手机执行 —— 唯一未知，靠 P0 定生死

**能复用多少**（照抄结构、代码落在本仓库）：无障碍服务生命周期、事件节流、心跳、保活、配置页、HTTP 客户端——这些 ddwx 都趟过了，省 2–3 天。

**要新写的只有一个 `ScanWorker`**：定时 `GET /scan/jobs` → 按步骤脚本执行 → `POST /scan/result`。

步骤脚本（配置化，申行者改版只改 YAML 不重新编译）：

```yaml
steps:
  - guard: {package: "com.sto.xxx", else: "abort"}          # 不在申行者就告警不扫
  - find:  {by: "className", value: "android.widget.EditText"}
    act:   set_text
    text:  "{waybill}"
  - find:  {by: "text", value: "确定"}                       # P0 确认到底是"确定"还是"确认"
    act:   click
  - wait:  {ms: 2500}
  - read:  {any_of: ["揽收成功", "已扫描", "已收件", "失败", "重复"], into: result}
```

必须内建的 5 个保护（每一条都对应一种真实事故）：

1. **包名校验**：当前前台不是申行者 → 立即 abort + 告警。否则会在微信/钉钉里乱点乱输入。
2. **重复单识别**：命中「已扫描/重复」 → 标 `dup`，**不重试**。认不出会被当失败无限重试，把队列卡死。
3. **单批上限**：默认 50 单/次，强制人工点「开始」。不做无人值守。
4. **失败留证**：失败时 `takeScreenshot()` 存图随结果上报，事后能看当时卡在哪一屏。
5. **单号校验前置**：PC 侧入队前已经把格式/前缀/长度验完，手机端不再判，减少一半分支。

## 4. 数据与协议

```sql
scan_jobs(
  id INTEGER PK,
  waybill TEXT NOT NULL,
  source TEXT,              -- excel / wx / manual
  source_ref TEXT,          -- 文件名+sheet+行号 / 群名+消息指纹
  status TEXT,              -- pending/running/ok/dup/fail/skipped
  attempts INTEGER DEFAULT 0,
  last_error TEXT,
  screenshot TEXT,
  created_at TEXT, scanned_at TEXT
)
UNIQUE(waybill)             -- 全库唯一，天然去重
```

```
GET  /scan/jobs?token=xxx&limit=1     → {"job": {"id": 12, "waybill": "7712345678901"}} / {"job": null}
POST /scan/result                     ← {"id":12,"status":"ok","raw":"揽收成功","cost_ms":1800}
POST /scan/heartbeat                  ← {"battery":88,"page":"申行者"}
```

失败分类要区分能不能重试：网络超时→重试（最多 2 次）；单号不存在/重量异常→不重试并告警；已扫描→`dup`；页面不对→告警停批。

## 6. 唯一阻塞点：手机怎么安排

你现在这台手机如果在跑 ddwx 钉钉采集，切到申行者那一刻，钉钉采集就停。三条路：

### 路线 A1｜加一台旧安卓（最干净，推荐）
专机跑申行者，ddwx 那台照旧。零改动、零干扰。**任何一台能装申行者的旧机都行**（安卓 7+、能插电常亮即可）。

### 路线 A2｜就用这一台，做「断档回补」
扫描期间不采集，扫完切回钉钉，**不重建基线**，而是往上补翻到断档起点。
- 可行性：UIA 树里有时间分隔条（`12:25`/`昨天 19:12`），可以按时间定位「补到哪停」。
- 代价：多写一个「补读」模块（约 1 天），且 ddwx 那边现在是「重建基线就吞消息」，得改它的接续逻辑——**这就碰了 README 的边界（不共用、不修改）**。
- 结论：能做，但要动 ddwx，且一旦出 bug 两边一起坏。**不推荐**。

### 路线 A3｜时段分离（零代码，最省事）
扫描只在固定窗口做（比如 19:00 后揽收完统一扫），这个时段本来就没有钉钉消息要转。
- 代价：白天来的单要等到晚上才扫。
- 如果你们的实际节奏就是「一批货到齐了才扫」，这条完全够用，**不需要第二台手机**。

**我的建议：先按 A3 跑通全流程，跑顺了再决定要不要买第二台旧机。**

## 7. 需要你定的三件事

### 7.1 手机是谁的
你现在说「可以登录安卓手机并插电打开申行者」——**这台是不是 ddwx 那台采集机？**
- 是 → 走 A3（先）或 A2（要改 ddwx）
- 不是 / 还能再找一台 → 走 A1，最省心

### 7.2 网点账号能不能开接口
一句话问你客户经理 / 网点管家：**「网点账号有没有开通『揽收扫描上传』的开放平台接口权限？」**
- 有 → 整个手机链不用做，一周内能完事，比什么都稳
- 没有 → 按本文做

### 7.3 扫描的是真实揽收件，还是补录历史单
- 真实揽收 → 半自动（人工点开始）即可，合规
- 补录历史 → 属于「人为生成虚假轨迹」，专项治理重点，罚款/封号风险。这种情况**必须**保留逐单人工确认，不能做成自动跑

## 8. P0 探针（0.5 天，4 个问题）

比 v1 的 6 项少了两项（微信解密、单条耗时可以并到 P1 测）。

| # | 问题 | 怎么验 | 不通的后果 |
|---|---|---|---|
| 1 | 扫描框是不是 `android.widget.EditText` | 手机开 USB 调试 → `adb shell uiautomator dump /sdcard/s.xml && adb pull` → 用 `ddwx-bridge/tools/android_probe/analyze_uiautomator.py` 分析（**工具现成**） | 不是 → 转 ESP32 假巴枪（+3 天 + ¥40） |
| 2 | 提交靠回车还是按钮，文案是「确定」还是「确认」 | 同上 dump + 人工点一次 | 步骤脚本按实际改，成本低 |
| 3 | 有没有「连续扫描」模式（扫完自动回输入框） | 人工连扫 3 单 | 没有 → 每单多点一次，速度减半，仍可做 |
| 4 | 重复单号提示什么文案 | 同一个号扫两次 | 认不出 → 队列会被卡死，必须拿到文案 |

**顺带值得抓一次**：申行者「蓝牙/WiFi 绑定巴枪」的设置页。若是 WiFi TCP 私有协议，可能连手机控件都不用碰，PC 直发。
