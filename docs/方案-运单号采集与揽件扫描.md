# 运单号自动采集 → 申行者揽件扫描｜可行性研究与方案（v1，未实施）

> 状态：**方案稿**，不含实现。日期 2026-10-19。
> 目标：从「指定微信群」「Excel 文件」两个来源采集指定前缀（如 77）的运单号，自动送入手机「申行者」App 的揽件扫描框，完成「确定 / 完成」动作。

---

## 一、需求拆解

这件事不是「一个功能」，是四个能力串起来的一条链，其中只有前两段是软件常规活：

| 段 | 要做什么 | 成熟度 | 主要风险 |
|---|---|---|---|
| ① 采集 | 从微信群消息里取文本 | 中 | 微信 4.x 不暴露 UIA，只能走本地库或 OCR |
| ② 采集 | 从 Excel 取运单号 | 高 | 几乎无风险，纯解析 |
| ③ 归集 | 识别、去重、排队、台账 | 高 | 无，纯本地逻辑 |
| ④ 执行 | 把号打进申行者并提交 | **低** | 控件能否被驱动、业务是否允许 |

**结论：①②③ 都能做，难点全在 ④；而 ④ 的成败取决于两条，必须在写代码前先验证。**

---

## 二、结论先说

**技术上可行，但有三个前置条件，任一不成立方案就得换。**

1. **申行者的扫描框必须能被程序写入**（标准 `EditText` 且暴露节点树）。
   - 成立 → 纯软件搞定，不用硬件。
   - 不成立（Flutter / 自绘 / WebView）→ 必须走「模拟蓝牙巴枪」路线，要一块 ¥20–40 的开发板。
2. **必须有一台『专职』手机跑申行者。**
   - 安卓同一时刻只有一个前台 App。现在这台手机在跑钉钉采集（要常亮、钉钉在前台），一旦切到申行者，钉钉采集就停，停的这段时间的消息会随基线重建一起被吞掉（这正是昨天「拦截单退单打印提醒」漏转的机制）。
   - 所以要么加一台旧安卓，要么接受「扫描时段不采集」。
3. **扫描行为必须对应真实揽收。**
   - 申通在专项治理「人为生成数据引起的虚假轨迹」。扫描即产生物流轨迹，若单号对应的件实际没收到，属于虚假揽件，风险是罚款 / 封号，不是技术问题，也修不了。
   - 建议做成「业务员点一下开始」的半自动，不做无人值守全自动。

## 三、写代码前必须先验证的 6 件事（P0 探针，半天）

这 6 个答案决定选哪条方案，**猜错一条就白写一周**。

| # | 验证什么 | 怎么验 | 不通过的后果 |
|---|---|---|---|
| 1 | 揽件扫描页的输入框是不是 `android.widget.EditText` | `dump_hierarchy` 看节点树 | 不是 → 只能走蓝牙巴枪 |
| 2 | 提交靠回车还是按钮，按钮文案是「确定」还是「确认」 | 同上 + 人工点一次 | 步骤脚本要按实际改 |
| 3 | 有没有「连续扫描」模式（扫完自动回输入框） | 人工连扫 3 单观察 | 没有 → 每单要多点一次，速度减半 |
| 4 | 单条耗时（提交到出结果） | 秒表 / 日志 10 单 | 决定批量 100 单是 3 分钟还是 10 分钟 |
| 5 | 重复单号的表现（提示文案） | 同一号扫两次 | 认不出重复 → 会被当失败无限重试 |
| 6 | 微信 4.1.15 的库能不能解密 | 跑一次 WeChatMsg 的 `1-decrypt.py` | 不能 → 微信群改走 OCR 或手机读 |

> 已验证的旁证：微信为 **4.1.15.53**（数据在 `C:\Users\Administrator\Documents\xwechat_files`），
> 而 WeChatMsg 官方标注适配到 **4.0.3**，4.1 需实测。
> 华为官方文档明确：**华为/鸿蒙没有「无线调试」设置项，只能用 USB 调试** —— 这直接影响 adb 路线。

## 四、GitHub 上找到的可复用件

| 项目 | 能用的部分 | 用不上的部分 | 风险 |
|---|---|---|---|
| **`LC044/WeChatMsg`（wxManager）** | 微信 4.x 本地库解密（`pymem`+`yara` 从进程内存取 key）+ 消息解析，直接读出群名/发送人/正文/时间，**精确、无需 OCR、不用抢窗口** | 导出 HTML/Word 那套 | 跟随微信版本，4.1.15 未验证；需管理员权限；杀软可能报 |
| **`openatx/uiautomator2`** | `d(text=...).set_text()` / `.click()` / `dump_hierarchy()` / `send_action("done")`，PC 侧 Python 直接驱动任何 App，**调试极快** | 需要 adb；华为无无线调试 | 手机重启后要重新插线 `adb tcpip` |
| **`oocsoo/ExpressDeliveryWeChatBot`** | 单号识别正则（申通/中通/圆通/韵达…）、多分隔符切分、消息指纹去重、Excel 台账、串行发送队列 | 它的微信接入（WebSocket 机器人，有封号风险） | 只用算法，不用接入方式 |
| **`gayandsilva/ESP32-BLE-Barcode-Scanner`** + `T-vK/ESP32-BLE-Keyboard` | ESP32 模拟 BLE HID 键盘，收到串口数据后「打字 + 回车」，正是扫码枪的行为 | 它的 GM67 扫码模块硬件 | 需买板子、写固件、配对一次 |

**额外发现（可能是最优解）**：申行者官方支持「通过**蓝牙或 WiFi** 绑定巴枪」。
- 若是蓝牙 HID → 上面的 ESP32 方案直接可用，App 以为是真巴枪，绕过所有控件限制。
- 若是 **WiFi/TCP 私有协议** → 可能连板子都不用，PC 直接按协议发单号（需抓包逆向）。这条值得在 P0 顺手抓一次。

## 五、五个方案

### 方案 A｜双手机 + 自研无障碍执行器（推荐做生产）

```
微信群 ─┐
        ├─→ PC 抽取/去重 → scan_jobs(SQLite) ─→ 手机轮询 /scan/jobs
Excel  ─┘                                        ↓
                                        申行者：setText → 确定 → 读回结果
                                                 ↓
                                        POST /scan/result → 台账 + 界面
```

- **手机侧**：在现有 `ddwx-collector` 里加一个「扫描执行器」模块（同一个无障碍服务，多一个能力）。
  PC 只存队列，手机每 2 秒 `GET /scan/jobs?token=` **主动拉**（复用现有 HTTP 通道，不用做推送，不用打洞）。
- **动作步骤做成配置脚本**，不写死：
  ```yaml
  steps:
    - {find: "输入框", by: "className", value: "android.widget.EditText", act: "set_text", text: "{waybill}"}
    - {find: "确定",   by: "text",      value: "确定",                    act: "click"}
    - {wait: 3, expect_any: ["揽收成功", "已扫描", "失败"]}
  ```
  申行者改版时只改配置，不改代码。
- 优点：不依赖 adb（只走 WiFi）、不受华为限制、复用现有 App/网关/心跳/配置/界面。
- 缺点：要写安卓端 Java；扫描期间这台手机不能干别的。
- 工作量：约 **5–8 人天**（含安卓）。

### 方案 B｜adb + uiautomator2（推荐做验证，不建议长期）

- PC 用 Python 直接调 `uiautomator2`，手机端零开发。
- 优点：**当天就能把整条流程跑通**，dump 控件树、截图、逐条调试都极方便；P0 探针就用它。
- 缺点：华为无「无线调试」，需先插一次 USB 执行 `adb tcpip 5555`，**手机重启后失效**；开发者选项可能被系统自动关闭；手机必须和 PC 同网段。
- 结论：**当开发工具用，不当产品用。**

### 方案 C｜ESP32 蓝牙「假巴枪」（最稳，需硬件）

- ESP32 作为 BLE HID 键盘，收到 PC 下发的单号后「打印 + 回车」；申行者以为是扫描枪。
- 优点：**完全绕开控件树**（哪怕扫描框是自绘的也能用），延迟最低，App 更新几乎无影响。
- 缺点：要买板子（¥20–40）、写固件、首次配对；Android 上 HID 输入需要焦点在目标框。
- 工作量：约 **3–4 人天** + 硬件。

### 方案 D｜人工辅助（今天就能用的兜底）

- PC 把两个来源汇总成一张「待扫清单」（界面里一列大号单号 + 一键复制下一条），业务员在申行者里逐条粘贴或扫码。
- 优点：零自动化风险、零合规风险、当天可用；还能顺便把「哪些单该扫、重复怎么办」的规则摸清。
- 缺点：不省人力。
- **建议与 A 并行先跑一周**，用真实数据校准规则，再上自动化。

### 方案 E｜申通开放平台 API（最正规，但要资质）

- 若有网点/商家账号能申请到「揽收扫描上传」接口，直接 HTTP 上报，**根本不用碰手机**。
- 现实：个人业务员基本申请不到，权限按网点开通。
- 一句话判断：**你们有没有能申请接口的网点账号？有的话这是唯一该走的路。**

### 方案 F｜进阶：同机并存（不改硬件，但要动采集层）

- 把钉钉采集从「无障碍读屏」改成「通知监听」（`NotificationListenerService`），钉钉在后台也能收消息，手机前台就能留给申行者。
- 代价：通知只给短消息预览，长卡片会被截断，等于**推翻我们花了很久才做稳的长消息补全**。
- 结论：**不建议现在动**，除非你坚决不加第二台手机。

## 七、推荐路线（分四期，每期可独立验收）

| 期 | 内容 | 验收标准 | 估时 |
|---|---|---|---|
| **P0** | 探针：dump 申行者揽件页、量单条耗时、试 3 条输入；顺带抓一次巴枪绑定协议；跑一次微信库解密 | 6 个问题全有答案 | 0.5–1 天 |
| **P1** | **Excel → 扫描**（不碰微信）：任务队列 + 手机执行器 + 结果回报 + 台账 | 50 条真实单号，成功率 ≥95%，失败有原因 | 3–5 天 |
| **P2** | 微信群采集：优先 DB 直读，不行退 OCR | 群里发 10 条测试单号，全部正确入队 | 2–4 天 |
| **P3** | 界面（待扫清单/进度/失败重试）、告警、开关、前缀配置 | 业务员可独立操作，出问题能自己看明白 | 3–5 天 |

**先做 P1 而不是先做微信采集**：扫描这一段是不确定性最大的，先把硬的啃下来，免得采集做完了发现送不进去。

## 八、数据与配置（草案）

```yaml
scan:
  enabled: false
  prefixes: ["77"]            # 可改、可多选
  lengths: [12, 13, 15]       # 允许长度
  regex: ""                   # 高级：自定义正则，留空用上面两条
  groups: []                  # 群白名单（空 = 不采集微信）
  excel_paths: []
  excel_columns: ["运单号", "单号"]
  interval_ms: 1200           # 每单间隔
  batch_max: 50               # 单次上限，防手滑
  require_confirm: true       # 开始前人工点一下
```

```sql
scan_jobs(
  id, waybill, source,          -- wx / excel / manual
  source_ref,                   -- 群名+消息id / 文件名+行号
  status,                       -- pending/running/ok/dup/fail/skipped
  attempts, last_error,
  created_at, scanned_at
)
```

**失败分类要区分「能不能重试」**：网络超时→重试；单号不存在→不重试并告警；已扫描→标 dup 不重试；状态不符→告警。

## 九、风险清单

| 风险 | 后果 | 缓解 |
|---|---|---|
| 扫描框不可写 | 方案 A 直接不可行 | P0 先验，验完再定 |
| 申行者改版 | 步骤脚本失效 | 步骤配置化 + 失败截图 + 告警 |
| 登录掉线 / 弹窗公告 | 队列卡死，静默不扫 | 每单前校验当前页，异常告警（复用现有失联告警通道） |
| 手机灭屏挂起（华为已知） | 扫描中断 | 保持唤醒 + 常亮 + 插电，与现有采集机同规矩 |
| 重复扫描 | 提示「已扫描」被当失败 | 识别 dup 文案，标 dup 不重试 |
| **虚假轨迹** | 罚款 / 封号 | 只扫真实揽收件；人工确认开关；留完整台账可追溯 |
| 微信群读不到 | 漏单 | DB 与 OCR 双路，任一路成功即入队；入队即台账，可人工补 |

## 十、需要你定的三件事

1. **有没有第二台安卓手机**（旧机即可）？没有的话只能在 D（人工）和 F（改采集层）之间选。
2. **申行者的揽件扫描，是扫真实收到的件，还是补录历史单**？后者合规风险高，我要按「不做全自动」设计。
3. **有没有能申请接口的网点/商家账号**？有的话优先走 E，手机这条链就不用做了。
