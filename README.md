## 一、运行方式：C++ 原生窗口 + 内置 Chromium 内核

双击 `运单自动采集自动揽收助手.exe`（C++ 编译的原生程序）：

1. 静默拉起 `core\miao-core.exe`（Python 后端：微信采集 / Excel 解析 / SQLite / HTTP 接口）
2. 等后端 8766 端口就绪，然后在**自己的原生窗口**里用**内置 Chromium 内核（CEF）**打开界面
3. 关窗口 = 全部退出（外壳会终止后端进程）

> **为什么用 CEF 而不是 WebView2**：实测这台机器上 WebView2 的 DirectComposition
> 合成层画不出来（窗口全黑，任何 GPU 参数都救不回，连纯净探针页都黑），而 Chrome
> 渲染正常。CEF 与 Chrome 同一套渲染路径，实测渲染完全正常。整包约 474MB，
> 其中 libcef.dll（Chromium 本体）占约 260MB——这就是「包内自带浏览器」的体积。
> Python 侧的 pywebview 路径（`desktop.py`）保留作为开发调试用，客户机分发只发 CEF 版。

### 构建命令（开发机）

```bash
.venv/Scripts/python.exe tools/fetch_cef.py        # 下载 CEF（首次，~171MB）
.venv/Scripts/python.exe tools/build_shell.py      # 编译 C++ 外壳 + 拷内核
.venv/Scripts/python.exe tools/package_shell.py    # 打包后端 + 组装 dist
.venv/Scripts/python.exe tools/make_installer.py    # 打成 setup.exe（需 Inno Setup 6/7）
```

产物：`dist/运单自动采集自动揽收助手/`（绿色目录，可直接拷给客户机）
和 `dist/运单自动采集自动揽收助手-Setup-<版本>.exe`（安装包，约 142MB）。

安装包行为：装到 `%LOCALAPPDATA%\Programs`、免管理员、桌面+开始菜单快捷方式、
自带卸载器；**不打包开发机的 `config.yaml` / `data/` / `inbox/`**（避免泄露 token 和
调试队列），首次启动现生成随机 token 并弹窗显示；卸载保留 `data/`，重装不丢队列。

版本号写在根目录 `VERSION`，改完重新编译即可。

### 人工只需要做一件事：启动程序

默认开启 **自动模式**（设置中心 → 自动运行）：

| 环节 | 自动做什么 |
|---|---|
| 微信群新消息 | 每 2.5 秒读一次当前会话，按时间范围过滤后提取单号 |
| 入库 | 单号唯一索引去重，来源、时间、原始文本一并留档 |
| 下发 | 每 3 秒检查一次，有积压且无进行中批次 → 自动开批，手机即可领取 |
| 重试 | 失败自动回队，超过次数转终态 `fail`，界面可单条重试 |

想回到「人工确认」：改 config.yaml 里 `scan.auto_mode: false`（一般不需要，全自动就是默认）。

## 快速开始（PC 侧，现在就能跑）

### 方式一：双击 exe（给业务员用）

```
dist/运单自动采集自动揽收助手/运单自动采集自动揽收助手.exe
```

双击即用：C++ 外壳（自带 Chromium 内核，机器上不用装任何浏览器）→ 静默拉起
Python 后端 → 打开程序窗口，关窗口就退出。
`config.yaml`、`data/`、`inbox/` 生成在 exe 旁边，升级只覆盖程序文件、数据不动。

界面上只有一个要点的按钮：**「开启服务」**。开了之后全自动：
盯群采集 → 自动入库 → 有积压自动开批（每批最多 500，超出的排下一批）→ 手机来领任务。
再点一下变「停止服务」，采集和下发全部待机。

重新打包：

```bash
.venv/Scripts/python.exe tools/package_shell.py   # 外壳+内核+后端 一条龙
```

### 方式二：源码运行（开发用）

```bash
python -m venv .venv
.venv/Scripts/python.exe -m pip install openpyxl pyyaml uiautomation comtypes pillow

.venv/Scripts/python.exe run.py init      # 生成 config.yaml（里面是随机 token）
.venv/Scripts/python.exe run.py check     # 自检：配置 / 数据库 / 端口
.venv/Scripts/python.exe run.py serve     # 界面 http://127.0.0.1:8766
```

流程：Excel 丢进 `inbox/`（或等微信群采集）→ 点「开启服务」→ 手机来领任务，剩下的全自动。

手机端要实现的三个接口（都带 `X-Token`）：

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/jobs/next` | 原子领取一条任务，没有则 `{"job": null}` |
| POST | `/api/jobs/{id}/result` | `{"status":"ok\|dup\|fail","raw":"揽收成功","error":"","screenshot":""}` |
| POST | `/api/heartbeat` | `{"page":"申行者","battery":"88"}`，界面上的「手机」卡片靠它 |

**服务开着且队列有单才会自动下发**；暂停/中止某个批次用批次条上的按钮。

已实现：单号识别（含 Excel 浮点/空格/横线/全角等坑）、去重（文件哈希 + 单号唯一索引）、服务总开关、自动开批 + 500 条自动拆批、失败重试（可重试 2 次）、重复单 `dup` 终态、中止退回队列、结构化日志、局域网 token 鉴权、审计事件表。
未实现：手机端 APK（待 P0）。

### 微信群采集（已实机跑通，2026-10-19）

```bash
.venv/Scripts/python.exe run.py wechat    # 采一轮就退出，用于现场排障
```

前置：微信停在目标群聊窗口。**群名和开关都能在界面上改**，不用动文件：

```
采集群  [自动揽收测试群，支持明文单号excel        ]  ☑ 启用采集  [保存]
```

保存后写两处（`runtime` 表即时生效 + `config.yaml` 重启仍有效），采集线程下一轮就按新群校验。
清空群名 = 暂停采集。人数后缀 `(3)` 不用写，程序会自动忽略。

也可以直接改 `config.yaml`：

```yaml
wechat:
  enabled: true
  group_name: 自动揽收测试群，支持明文单号excel   # 人数后缀 (3) 会自动忽略
  file_root: ""        # 留空自动探测 ~/Documents/xwechat_files
```

两条通道，去重逻辑完全不同，这是设计上的关键：

| 通道 | 取什么 | 怎么去重 | 首轮行为 |
|---|---|---|---|
| 文字消息 | `mmui::ChatTextItemView` 的正文 | 指纹基线（`sha1(类型+正文)` 存 runtime 表） | 只记基线，**不采历史** |
| 文件消息 | 气泡里的「文件名 + 大小」→ 去接收目录找实体文件 | **内容 sha256**（`imports` 表） | **立即采**，因为幂等 |

文件消息为什么能首轮就采：气泡本身不含单号，必须去
`~/Documents/xwechat_files/<wxid>/msg/file/<YYYY-MM>/` 找实体表格再解析。
同一份表处理一次和处理十次结果相同，所以不需要等第二轮，重启也不会重复入库。

**为什么必须靠「大小」认文件**：群里每天发 `丹鸟.xlsx`，微信存本地时依次改名成
`丹鸟(15)(16)(17).xlsx`，光看文件名根本不知道消息指的是哪一份。但气泡里带着
`10.8K`，本机 `11051` 字节正好吻合，而 10 月 2 日那份旧 `丹鸟.xlsx` 是 `10.5K`，
一比对就排除了。匹配规则：**基名相同 + 大小差 ≤0.15KB + 取最新 mtime**。

已实测的两个坑：

- **`max_row=1048576`**：业务员发来的表常带一个被拉到 104 万行的格式残留
  （`dims=A1:A1048576`），openpyxl 会老实遍历完。已加短路：连续 200 行全空即收工，
  519 行的表从 104 万次降到 520 次，0.2s → 0.02s。
- **非申通单号是正常的 0**：`丹鸟.xlsx` 里 30 个 `621` 开头的单号会被前缀规则
  全部过滤掉，这是对的，不是漏采。

### 单号规则（界面上可改，不用动文件）

界面上「单号规则」一栏填两个框，点保存立刻生效：

| 项 | 含义 | 例子 |
|---|---|---|
| 前缀 | 单号开头几位数字，逗号分隔 | `77, 621`（77＝申通，621＝丹鸟） |
| 位数 | 单号长度，逗号分隔 | `12, 13, 15` |

也可以直接调接口：

```bash
curl -X POST http://127.0.0.1:8766/api/settings/scan \
  -H "X-Token: <token>" -H "Content-Type: application/json" \
  -d '{"prefixes":"77,621","lengths":"15"}'
```

改一次写两处：`runtime` 表让**当前进程立即生效**（采集线程下一轮就读新值），
`config.yaml` 让**重启后仍然是这个值**。

关键点：**改了规则，已导入的表格会自动重新解析一遍。** 去重键是
`sha1(文件内容) + sha1(前缀|位数)`，规则变了键就变了。所以「一开始只认 77，
丹鸟那份表进了 0 条；后来加上 621」这种情况，丹鸟的 30 条能补进来，
而已经入队的 519 条不会重复。没有这个设计，新规则对旧表永远不生效——
文件一个字节都没变，内容哈希完全相同，会被当成「已导入」直接跳过。

## 一、与「喵喵钉钉-微信消息转发桥」的关系：完全独立

这是**两个软件**，不是同一个程序的两个模块。边界如下，任何一条都不许破：

| | 钉钉-微信转发桥（`ddwx-bridge`） | 本软件（`sto-scan-assistant`） |
|---|---|---|
| 干什么 | 钉钉群消息 → 微信群（单向） | 微信/Excel 运单号 → 申行者 App |
| 代码 | 自己的仓库 | 自己的仓库，**不 import、不同步、不共用** |
| 配置 | `config.yaml` | 自己的配置，**互不读取** |
| 数据库 | `data/bridge.db` | 自己的库，**不共用一张表** |
| 进程 | 自己的一套 GUI + worker | 自己的进程，**互不拉起、互不 kill** |
| 手机端 | `ddwx-collector`（读钉钉） | 自己的 APK（写申行者），**包名独立** |
| 安装目录 | `C:\Program Files\喵喵钉钉-微信消息转发桥` | 自己的目录 |
| 网关端口 | 8765 | 自己的端口，**不要复用 8765** |

**为什么不合并**：两边的前台/端口/数据库/升级节奏完全不同。转发桥是「一直挂着、不能断」的采集链路；本软件是「按需批量执行」的作业工具。混在一起，任何一边升级或崩溃都会带上另一边。

**可以借鉴、不许依赖**：单号正则、去重指纹、步骤脚本这些思路可以直接照着写，但代码要落在本仓库里，不能 `from bridge.xxx import`。

## 二、三条硬约束（方案的核心结论）

1. **手机要一台专职的。** 安卓同一时刻只有一个前台 App。现役采集机切到申行者 = 钉钉采集停 =
   那段时间的消息随基线重建被吞（转发桥已踩过这个坑）。要么加一台旧安卓，要么接受扫描时段不采集。
2. **扫描框必须可写。** 标准 `EditText` → 纯软件方案；自绘 / WebView → 只能走「模拟蓝牙巴枪」（ESP32，¥20–40）。
3. **扫描即产生物流轨迹。** 申通在专项治理虚假轨迹，不做无人值守全自动，保留人工确认闸。

## 三、开工前必须先验证（P0 探针，半天）

不知道这 6 个答案就不要写代码，猜错一条白写一周。

- [ ] 揽件扫描页的输入框是不是 `android.widget.EditText`（`dump_hierarchy` 看节点树）
- [ ] 提交靠回车还是按钮，按钮文案是「确定」还是「确认」
- [ ] 有没有「连续扫描」模式（扫完自动回输入框）
- [ ] 单条耗时（提交到出结果，测 10 单）
- [ ] 重复单号的表现（提示文案）—— 认不出重复会被当失败无限重试
- [ ] 微信 **4.1.15.53** 的本地库能否解密（WeChatMsg 官方只标到 4.0.3）

顺带值得抓一次：申行者「蓝牙 / WiFi 绑定巴枪」的协议。若是 WiFi TCP 私有协议，可能连硬件都不用。

## 五、目录规划（未来，现在还没建）

```
sto-scan-assistant/
├─ app/            桌面端界面（与转发桥同风格，但独立进程）
├─ scan/           核心：单号识别、去重、任务队列、台账
│  ├─ extract/     来源采集（wechat / excel）
│  └─ executor/    手机执行器（对外 HTTP 接口）
├─ android/        手机端 APK（扫描执行器，包名独立）
├─ docs/           方案与设计
└─ tests/
```

技术选型倾向：Python（与现有人力/经验一致）+ SQLite + 标准库 HTTP；手机端原生 Java（无障碍 `ACTION_SET_TEXT` + `ACTION_CLICK`），动作做成配置化步骤脚本，申行者改版只改配置。
